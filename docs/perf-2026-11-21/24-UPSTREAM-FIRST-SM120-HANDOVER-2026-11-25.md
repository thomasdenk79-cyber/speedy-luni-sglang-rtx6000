## 1. Decision and evidence
- Freeze the fast HyperBurst-derived donor as Last Known Good (LKG), a performance/correctness oracle and rollback, NOT the permanent development base. Build the next **main engine on compatible recent official SGLang sources**, re-applying only useful HyperBurst and local deltas. Keep a donor-side native NVFP4 experiment in parallel if it is already underway, then port the winning implementation forward. Do not restart the campaign merely to change branch names.
- No full-stack version upgrade in place. Latest coherent tuple beats highest independent version numbers. Recent official release and main/nightly are separate candidates, with exact engine and dependency SHAs. A clean upstream engine can be slower initially; measure the delta and recover the specific missing optimizations. It is not accepted for production until it meets the LKG Pareto gate. Never replace LKG with an unqualified upstream build.
- NVFP4 is the default research hypothesis, not a forced universal precision. Eliminate avoidable global-memory materialization, conversion, launch overhead and duplicate weights before deciding a numerical format has failed. W4A4 native block-scaled MMA, W4A16 fused register/shared-memory dequant and W4A8 (where supported) are distinct contracts. FP8 is also hardware-supported. Narrower weights do not imply 2x real application speed; runtime quantization, scheduling, sparsity, launch, occupancy and activation errors matter.
- Quality and speed are joint primary axes. VRAM, capacity, peak workspace, latency tails and stability are additional axes. Keep trade-offs explicit; a dominated candidate is research evidence, not a production win. Reuse already-completed C1–C10 sweeps as references where build/flags/corpus match; do not repeat the whole campaign for every patch. Re-measure only affected paths and final combined release.
- HiCache/NIXL/SSD experiments deferred; PLE stays pinned RAM; do not introduce host offload as a workaround for core hot-path overhead. No change to live port 8001; :30000 remains normal service port. CPU-only work until an authorized GPU window.
- Existing evidence [23](23-DENSE-FIXED-VERDICT-2026-11-25.md), [KV](../../bench/DONOR-NVFP4-KV.md), [profile](../../bench/DONOR-NVFP4-PROFILE.md): 509760 FP8-KV → 866496 NVFP4-KV slots (+70%, with configuration/provenance caveats); dense fixed 947392 (+9.3%) with equal 242/250 GSM8K, 218/250 MMLU totals, but cold prefill ~19% slower. P0.2 per-call FP8 requant worsens control; P0.2b cache 763392 KV and ~4–5% prefill below original FP8-dense baseline, therefore dominated on those metrics. Preserve P0.2/P0.2b as diagnosis, off by default; not a release promotion. Identical aggregate scores do not establish paired equivalence. The C8 thermal drift is confounded, not proof of a kernel regression.
- Existing profile (short decode, 40 steps) FP8 dense 36.6/27.2%, MoE 21.8/37%, HC 12.7/9.6%, GDN 4.2/6.7%, indexer 3.7/2.4%, Cake 1/1.1% (C1/C4). Use it as a prioritization hint, not exact critical-path shares. Profile long-context and prefill separately.

## 5. Native NVFP4 design contract
For qkvz N=16384 K=2560: per matrix FP8 40 MiB (plus scales), NVFP4 20 MiB payload +2.5 MiB E4M3 K/16 scales + global scalar; BF16 80 MiB. For 36 layers, ideal FP8→NVFP4 saves ~630 MiB (excluding workspace); do not conflate with allocator-derived capacity. P0.2b extra FP8 copy ~40 MiB/layer, measure exact affected layer count.
- Canonical packed weight [N,K/2] low nibble even K, raw E4M3 scale bytes [N,K/16], global FP32 scale per donor. Confirm with packer and FP32/BF16 reference. Native kernel layout may be transposed/swizzled; use one physical payload if possible, prepack once and adapt other kernel; scale-only duplicated if necessary and accounted. A temporary repacked copy is acceptable for isolated kernel discovery, not production default.
- For A4 quantize activations once per needed projection (fuse RMSNorm/quant where compatible); measure quantization and GEMM together. For A16 read packed weights directly and dequant inside kernel, not an expanded HBM tensor. A8 requires proven scale contract; do not label all mixed operand paths as native hardware NVFP4 MMA.
- Test original BF16 weights vs baseline FP8 vs NVFP4 from BF16, separately weight-only W4A16 and W4A4. Keep fixed original activation samples (real layers, prefill, decode, verify, outliers). Measure per-layer output RMSE/relative error, cosine, max/NaN/Inf, logit KL/top-k agreement, final accepted length and end-to-end. Model quality gates not bitwise for deliberately different quantization; bitwise or tighter reference for same arithmetic/routing changes where required. 4over6 offline weight scales separate experiment from activation quant. No double quantization without documentation.
- Shape sweep M=1,2,4,8,16,32,64,128,256,512,1024,2048,4096,8192 (plus live shape histograms and graph padding). Compare actual kernel+quant+packing cost, cold/warm graphs, workspace, DRAM bytes and CUDA event latency. No full 70-minute run for candidate that fails native route, numerical screen or both axes. Determine crossover per shape/phase; verify path with MTP, direct projection hook and captured graphs.
- SM120 instruction family: mma.sync.aligned block-scaled, confirm PTX/SASS and Nsight metrics. SM100 tcgen05 is not same. Reject unsupported shapes with explicit reason before launch, verify known sentinel/NaN-poison tests and allocator race with concurrent streams.

## 6. KV capacity and scheduler budget
Keep NVFP4 KV default candidate even if C4 fits FP8. Lower bytes/token increases effective bandwidth when that path is bandwidth-bound; short decode Cake only ~1% of profiled GPU time, so don't infer large global gain. At long contexts, inspect actual sparse selected K count, state slots, page padding and cache retention. KV pool slots are not per-request context or guaranteed concurrency. For 866496 slots, 8 × 100k nominal fits before reserves; 4 × 250k does not. Budget: sum live unique cached prefixes + new input + generation/verify/allocator reserve; Mamba/SSM admission independent. Compare at (a) fixed logical KV cap/shape to isolate kernel and (b) same VRAM budget to show usable extra capacity. Report evictions/recompute, actual active requests and TTFT/ITL p95. Context 262144 currently caps each request; raising to 500K requires separate supported context setting and state/pool validation.

## 7. Tokenmap: establish whether it is needed, whether it works, and what it costs
### Existing evidence / corrected interpretation
Read [DONOR-LRU-ABLATION](../../bench/DONOR-LRU-ABLATION.md), [LRU8 qualification](../../bench/DONOR-LRU8-QUALIFICATION.md), [actual patch](../../patches/donor-lru/0001-spec-add-fully-replaceable-LRU-to-the-donor-mixed-dr.patch), [coding replay](../../bench/coding-map-replay.py). LRU8 combined map policy, C4→C8 admission, graph sizes and Mamba slots, also changed bank-wide vs subset scale. C1–C4 -0.5..-2.1% is not isolated evidence. CPU oracle (512 batches), synthetic graph stable buffers and live demotions demonstrate replacement occurs; do not prove next-token prediction benefit, full logit path, or net overhead. Existing coding replay runs fixed synthetic transcripts sequentially, fabricated test outputs, warmed map; it is not execution-based coding evaluation or causal A/B.
- Donor: 49152 static NVFP4 + 256 FP8 FIFO = 49408; LRU primary 49152 total (48896 packed + 256 FP8), recurrent 33024, no pinned IDs. **Normalize row counts and dtype/scale/source bank for policy-only A/B**, rather than equating 49408 with 49152. Keep target full vocabulary 248320 unchanged.
- A same-size dynamic map cannot directly accelerate its LM GEMV. Only better proposal distribution/acceptance, fewer verification rounds, or smaller shortlist at same acceptance can improve throughput. Full vocab could yield higher acceptance at extra head cost; no-map must be measured. FR-Spec is a drafter-only optimization; verify full target distribution, token ID mapping, EOS/tools, greedy equality vs no speculation and statistical sampling correctness where supported. Never restrict target logits to shortcut quality.
- LRU observe() has torch.topk over entire age array on every update, scatter_reduce/cumsum/index operations, then four index_copy_ per head. It calculates and performs sink copies even if no valid admission (masked source row 0); two independent heads double work. Prefill chunks of 4096 may cause substantial dummy row traffic. Confirm with profiler, not assumptions. Global packed source bank for hidden 2560 costs ~341 MiB for 248320 rows + metadata, target FP8 already resident if reused; measure unique storage, allocator and temporary gather, not summed tensor views.
- Pure prompt recency can pollute map with one-off log identifiers, repeated cached prefixes, tool dumps, uncommon prompt-only tokens. Need coverage on future target/draft output, not input hits. Repeated prefill observations and accepted-lens mask, primary/recurrent head update order, concurrent requests, CUDA stream synchronization, snapshot/version consistency are risks to audit. No claim of a race or broken LRU without reproduction.
